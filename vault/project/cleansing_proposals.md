# Cleansing proposals

No cleansing is applied without a decision. For each data quality issue: the **logic** that defines it, what the **exploration** showed (SQL with results: `analyses/00_data_quality_issues.sql`), the **business case** (Enpal sells solar systems to households through a consultative sale recorded in Pipedrive, see [[business_context --keep]]), my **assumption**, and the **proposal** for staging or intermediate. Every proposal is an assumption to confirm with the stakeholders ([[approach -- keep]]); the decisions below are the defaults implemented. Each issue has a singular test in `tests/data_quality/` that lists its affected raw rows in the Elementary report.

Principle: staging never drops a row whose meaning is unclear. It keeps the row, adds a key that is unique and a flag that names the issue, and leaves the business rule to intermediate, where it is visible and reversible.

## 1. Duplicates

How duplicates appear in a CRM like Enpal's: the same household sends several requests (web form, partner, comparison site) and gets several deals; a rep creates a deal that already exists; an import or a sync runs twice; a rep merges two deals (Pipedrive keeps the surviving deal's id and deletes the other). In Pipedrive, ids are sequential and never reused, and a user's email is the login, so it is unique per company account.

| # | Issue | Logic | Exploration | Assumption | Proposal |
|---|---|---|---|---|---|
| DUP-1 | Full-row duplicates | all columns equal | 0 in `deal_changes`, `activity`, `users`; the natural ids are not unique (`activity_id`, `deal_id` per lifecycle), the full row is | no double load in this export | **Decided (owner, 2026-10-23):** `deal_changes` has no natural key: staging builds `deal_change_key` with `dbt_utils.generate_surrogate_key` over all four columns and keeps the first row per key (0 removed today, 15,406 keys). `activity` gets **no** surrogate key: it is deduplicated on `activity_id` as its primary key (DUP-3). Removed rows are monitored on the raw data (warn) and reconciled in staging (raw rows - removed rows = staging rows) |
| DUP-2 | One `deal_id`, two lifecycles (D3) | more than one `add_time` event per deal | 5 deals, 17 repeated events, all in these 5; each lifecycle has its own creation, owners, stage path and lost reason, and its own clock time; lifecycles overlap; 2.2 such collisions expected by chance from random ids (5 observed, about 7% likely) | **two different deals under one id**: an id collision of the export (as in DUP-3), or a Pipedrive merge whose history was kept. Not one household entered twice: different owners, both lifecycles run on independently | **Split** into two deals: `deal_key` = `deal_id` + lifecycle number (by creation time), events assigned by the clock time of their lifecycle; flag `has_shared_deal_id`. Step totals then count 2,000 deals. Alternative: keep one deal and count first entries only (earlier proposal; mixes two deals' paths). The clock-time rule works because each lifecycle keeps its creation time of day (D5); with other data the merge record is needed. The trial merge test would tell whether Pipedrive keeps the merged deal's history |
| DUP-3 | One `activity_id`, two activities (A1) | more than one row per `activity_id` | 11 ids, 22 rows; all 11 pairs differ in user, deal and due date; 11.6 collisions expected by chance | **Decided (owner, 2026-10-23): `activity_id` is the primary key**; the two rows of an id are two versions of the same activity | **Decided: deduplicate on `activity_id`**, keep the row with the latest `due_to` (the current version; the export has no update timestamp): `row_number() over (partition by activity_id order by due_to desc) = 1`. 4,579 rows to 4,568, 11 removed. Impact with done calls only: steps 2.1 and 3.1 each lose 1 in 2024-01 and 1 in 2024-04. The evidence that the pairs may be different activities (different user, deal and date; chance collision rate) stays documented for the stakeholder review |
| DUP-4 | The same activity under two ids | same type, user, deal and due time | 0 groups | no call entered twice | Nothing to cleanse; no test needed beyond DUP-1 |
| DUP-5 | Users sharing an email (U1) | more than one user per email | 4 emails, 2 users each, different names; 21 names shared by 42 users, all with their own email | different people; in Pipedrive the login email is unique, so a shared email means edited user data, not one person twice | Keep all users; `lower(trim(email))`; flag `has_shared_email`; never join or deduplicate on email or name |
| DUP-6 | Duplicate leads (one household, two deals) | lost reason Duplicate Entry; same creation day and same owner | Duplicate Entry on 15 to 22% of deals at every stage (87 reached stage 8); 5 same-day same-owner pairs, hours apart, different paths, none marked Duplicate Entry | **the lost reason does not mark duplicates** (a real duplicate is closed early); no duplicate leads can be identified from this export (no household, address or contact fields) | **Decided (owner, 2026-10-25):** exclude Duplicate Entry deals from the funnel count. `int_pipedrive__deals` drops every deal with a Duplicate Entry lost reason (lost reason 5), also when it is not the deal's last lost reason (D3), so the report counts the remaining deals only. |

## Decisions for the owner

1. DUP-2: split the 5 deals into two deals each (proposed), or count once by first entry.
2. ~~DUP-3~~ decided: `activity_id` is the primary key; deduplicate, keep the latest `due_to`.
3. ~~DUP-1~~ decided: surrogate key on `deal_changes` only, deduplication on that key.
4. ~~DUP-6~~ decided: exclude Duplicate Entry deals from the funnel (filtered in `int_pipedrive__deals`, also when Duplicate Entry is not the deal's last lost reason).
5. ~~X1~~ decided: report window = first to last month with data; no hardcoded dates.
